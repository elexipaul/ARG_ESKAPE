# CARD dataset extraction and preparation

## Reference data source

Reference sequences were obtained from the Comprehensive Antibiotic Resistance Database (CARD)'s "protein homolog model" set, in both nucleotide (`nucleotide_fasta_protein_homolog_model.fasta`) and protein (`protein_fasta_protein_homolog_model.fasta`) FASTA form, together with CARD's `aro_index.tsv` ontology table (ARO Accession -> AMR Gene Family mapping).

## Header parsing

CARD's FASTA headers were parsed into a structured table using regular expressions anchored on the literal `ARO:` token rather than on fixed field position, since a subset of CARD gene names themselves contain multiple words and would otherwise split incorrectly. The nucleotide header format additionally encodes strand and 0-based, end-exclusive genomic coordinates relative to the source GenBank record; coding-sequence length was computed directly from these coordinates. Parsing succeeded for all 12,118 nucleotide and protein header records (6,059 of each), with zero unparseable headers. Three independent checks validated this: coding-sequence length computed from header coordinates matched the sequence length counted directly from the FASTA file for every nucleotide record (0 mismatches); every nucleotide coding-sequence length was evenly divisible by three (0 failures); and distinct ARO accessions totaled exactly 6,059, matching one nucleotide and one protein record per accession. 232 of the 12,118 records carried no organism annotation in the header; 674 distinct source organisms were represented among the remainder.

## Joining AMR Gene Family annotations

Each reference record was annotated with its AMR Gene Family by joining on ARO accession against `aro_index.tsv`. Because `aro_index.tsv` contains a small number of ARO accessions duplicated across multiple GenBank deposits (verified to carry an identical family value in every such case), the join used a deduplicated accession-to-family lookup, with an explicit assertion that no accession resolved to more than one distinct family before applying it; the join completed with zero unmatched records.

## Correcting multi-family representation

An initial join treated `AMR Gene Family` as a single-valued field and therefore mishandled genes that CARD's own ontology genuinely assigns to more than one family simultaneously -- for example, TolC, the shared outer-membrane channel component of the ABC, MFS, and RND efflux-pump systems, which CARD's `aro_categories.tsv` lists as three separate, independently-accessioned categories. The initial approach copied these semicolon-joined combination strings through as single phantom labels (e.g. one label reading "ABC...;MFS...;RND..."), rather than representing true multi-family membership. This was identified and corrected by exploding the `AMR Gene Family` field on `;` before the join, producing one row per (reference record, family) membership and joining via a relational merge rather than a scalar map. The scope of the correction was quantified directly against the data: 184 of 6,463 rows in `aro_index.tsv` carried a multi-valued family field (41 distinct combinations observed), and exploding this increased the reference table from 12,118 to 12,412 rows. Pre-existing downstream outputs that derive family labels from RGI's per-genome output rather than from `aro_index.tsv` were checked and confirmed unaffected by this correction.

## Splitting into per-family protein FASTA files

Using the corrected, exploded family assignments, the protein reference set (6,059 sequences) was partitioned into one multi-FASTA file per AMR Gene Family (396 files), with each header shortened to a `family-short-code_ARO-accession` form (e.g. `f1_3002999`) to avoid compatibility issues in downstream feature-extraction tools with CARD's full pipe-delimited headers. A protein record belonging to more than one family was written once into each family's file, deliberately, rather than assigned to a single family or discarded -- reflecting the one-vs-rest classification design used downstream, where each family-membership instance is an independent positive example for that family's model. This produced 6,206 (sequence, family) records across the 396 family files from the 6,059 source protein sequences, with zero records failing to match a family. One filename-level accommodation was required: the family name "Serine/threonine kinases" contains a character (`/`) that would otherwise be read as a path separator; only the output filename substitutes `_` for this character, leaving the family name as stored in the data itself untouched.

## Deduplication to individual protein records

Separately, for all-vs-all pairwise sequence alignment (which does not need to realign the same sequence once per family it belongs to), the 396 family FASTA files were parsed back down to one deduplicated multi-FASTA holding each of the 6,059 distinct protein records exactly once. The 6,206-to-6,059 gap was confirmed to be entirely attributable to genuine multi-family membership (126 proteins in 2 families, 9 in 3, 1 in 4: 126x1 + 9x2 + 1x3 = 147 extra copies, matching the observed gap exactly) rather than any data error, and every duplicate copy of a given record was verified to carry a byte-identical sequence before collapsing. Records belonging to multiple families retain all of their family short codes concatenated in the output header (e.g. `f63_f64_3000005`), ordered numerically rather than lexicographically (since, e.g., 'f165' < 'f37' under plain string ordering).

## What feeds the classifier

The per-family FASTA files (6,206 sequence-family records across 396 families) are the direct input to the feature-extraction notebooks (Pfeature- and ProFET-style), not the deduplicated 6,059-record set -- that deduplicated set is used only for the separate pairwise-alignment analysis. `family_classifier_importance.ipynb` subsequently restricts this to the 84 families with at least 10 sequences (5,479 sequences), as described in the Methods section.

## Data-quality notes

- Every quantitative claim above (record counts, match counts, the 147-record multi-family gap) was verified directly against the pipeline's own printed execution output, not asserted from the code alone.
- Multi-family genes were deliberately retained as multiple positive examples rather than assigned a single "primary" family or dropped. This means a small number of sequences (136 of 6,059, approximately 2.2%) contribute to more than one family's one-vs-rest training set -- a documented design decision consistent with CARD's own multi-family ontology, not an artifact of the extraction process, but worth noting that these 136 sequences are not strictly independent across the families they belong to.
- 232 records (1.9% of 12,118) have no organism annotation; this field is not used anywhere in the downstream feature-extraction or classification pipeline, so its absence has no effect on the classifier.
- All joins and corrections in this pipeline were validated with explicit assertions and printed match/mismatch counts at each step (0 unmatched in every join described above) rather than assumed to have worked silently.

# Feature extraction and representation

Two independent, complementary feature sets were computed directly from the per-family protein FASTA files described above, keyed identically (`sequence_id` from the FASTA header, `family` from the filename) so the two could later be joined on those columns.

## Composition-based features (Pfeature)

The first set was computed with the `pfeature` package (its `pfeature_comp` command-line tool), run separately for sixteen feature modules: amino acid composition, dipeptide composition, physico-chemical property composition, atom composition, bond composition, repetitive residue information, property repeat information, distance distribution of residues, Shannon entropy at the protein and residue level, a shared-property composition module, conjoint triad descriptors, pseudo amino acid composition, amphiphilic pseudo amino acid composition, quasi-sequence-order, and sequence-order-coupling number. Three modules in the installed package (tripeptide composition and two others) were excluded after being timed directly and found not to complete within 25 seconds on a handful of short test sequences, making them impractical at the scale of the full dataset; two further modules were excluded because they call a pandas function removed in pandas 2.0 and crash outright on the installed pandas version. Pfeature's evolutionary-information (PSSM), structure-based, and pattern modules were not available through the installed package at all -- those require a separate download, PSI-BLAST, and external structure-prediction tools, none of which were part of this extraction.

Two implementation issues were found and corrected while building this extraction, both confirmed directly rather than assumed: first, the tool's raw output carries no sequence-identifier column at all, relying entirely on row order matching the input FASTA's record order -- verified directly with a synthetic test FASTA before trusting this, and sequence identifiers were reattached from the parsed FASTA headers after each run rather than assumed to already be present. Second, the installed package writes its intermediate scratch files to a fixed, non-unique filename in the process's current working directory for every job it runs; running multiple extraction jobs at once from a shared working directory caused one job's output to silently disappear with no error and no failing exit code. This was caught directly during testing, not anticipated in advance, and fixed by giving every individual extraction call its own isolated temporary working directory. Sequences containing non-standard residue codes were flagged during a pre-flight scan but not automatically excluded, since this dataset is already known to contain at least one broken partial CARD reference entry, and silently dropping flagged sequences was treated as a decision for later review rather than one to make automatically inside the extraction step.

## Biophysical features (Biopython, ProFET-style)

The second set reimplements ProFET's global biophysical property category using Biopython directly, rather than the original ProFET package, computing ten properties per sequence: length, molecular weight, isoelectric point, aromaticity, instability index, GRAVY (hydropathy), net charge at pH 5, 7, and 9, and the aliphatic index. Aliphatic index is not a built-in Biopython method; it was computed from Biopython's own amino-acid-percentage output using the established Ikai (1980) formula. Each of the ten properties was additionally computed on three non-overlapping thirds of each sequence (N-terminal, middle, C-terminal), each only when that segment held at least five residues, giving forty feature columns per sequence in total.

Feature computation here is deliberately isolated at the level of the individual property, not the sequence or the file: an earlier version of this extraction failed the entire batch outright on the first sequence containing a non-standard residue. In the corrected version, a non-standard residue causes only molecular weight, instability index, and GRAVY to fail for that one sequence -- confirmed directly, by checking which of the underlying Biopython calls do and do not tolerate a non-standard residue -- while isoelectric point, aromaticity, the three net-charge values, and the aliphatic index are computed normally for the same sequence. Affected cells are recorded as missing values rather than the sequence being dropped, and a summary of exactly which columns were affected, and how often, was generated directly from the real output rather than assumed.

## Combining into master tables

Each extraction was run per family, written to its own per-family CSV, and then row-bound across all families into two master tables -- one from the Pfeature run, one from the Biopython/ProFET-style run -- each carrying `family` and `sequence_id` as the first two columns, with every other column a numeric feature. Because both extractions were built against the same per-family FASTA files and keyed identically, the two master tables can be joined directly on `(family, sequence_id)`; that join, and the cleaning applied to the result (imputation, zero-variance-column removal, and the PDC beta-lactamase-specific correction), is described in the Methods section rather than repeated here.

# Feature selection and reevaluation of classifiers

## Feature selection

Two distinct, and importantly not equivalent, forms of feature reduction were applied. The first is simple removal of degenerate columns: after merging and cleaning the two feature tables, five columns carried zero variance across the dataset and were dropped outright, since a constant-valued column carries no classification signal and cannot contribute to any model regardless of method. This is the only step at which a feature is permanently removed from what the classifiers are trained on -- every one-vs-rest model and the single multiclass model are both fit on the complete remaining feature set (1,035 columns), not on any further-reduced subset.

The second, and more substantial, form of feature reduction exists specifically to make computing feature importance tractable, not to reduce what the models are trained on. Naive permutation importance evaluated across the complete 1,035-feature set was timed directly and found to take approximately nine hours across all 84 families, which was not a viable approach to run routinely. Instead, a two-stage design was used: free gain-based importance, already produced as a byproduct of each fitted model at no extra computational cost, was used to shortlist the top 80 candidate features within each cross-validation fold, and permutation importance (five independent reshuffles per feature, averaged) was then computed only against that shortlist. SHAP values, by contrast, were computed against the complete feature set in every fold, not the shortlist, and were treated as the primary importance signal precisely because permutation importance is known to understate the importance of features in a shortlist-restricted, redundant-feature regime -- discussed further in the Methods section. In short: feature *selection*, as this term is usually meant (training on fewer features than are available), was not performed; what was selected is which features' importance gets the more expensive permutation-based estimate, with SHAP and the model itself always seeing the full feature set.

## Reevaluation of classifiers

The one-vs-rest classifiers were evaluated in two passes rather than one. The first pass, built alongside training itself, computed only threshold-free, cross-validated AUC and average precision from out-of-fold predictions. A second, later pass reevaluated the same already-trained, already-cross-validated models against a broader set of metrics: accuracy, F1, and confusion-matrix counts at a fixed 0.5 probability threshold, summarized both per family and as a single row-normalized confusion-matrix grid across all 84 families, together with an aggregate ROC-curve overlay highlighting the weakest-performing families by name.

This reevaluation changed what could be said about the classifiers' performance in two concrete ways. First, it surfaced a real, non-trivial tail of families that the AUC/AP-only view did not make as visible: ranked by AUC, `vanS` was the clear worst performer (AUC 0.584, F1 0.011, 12 positive sequences), followed by `16S rRNA methyltransferase (G1405)`, the ABC-F subfamily, `lincosamide nucleotidyltransferase (LNU)`, and the small multidrug resistance (SMR) efflux pump -- and this reevaluation confirmed directly that low sample size alone does not explain this tail, since several other families with equal or fewer positive examples (for example `OXA-12-like beta-lactamase` at 11 positives) reached the AUC = 1.0 ceiling. Across all 84 families, mean AUC was 0.968 and median AUC 0.9999, with 52 of 84 families at the AUC = 1.0 ceiling and 32 of 84 at the AP = 1.0 ceiling. Second, this reevaluation produced a direct, concrete demonstration of why accuracy should not be reported alone: `AAC(6')-Ib-cr` reached 98.5% accuracy at the 0.5 threshold while its F1 score was only 0.198, since with only 10 positive sequences among 5,479 total, a classifier can score highly on accuracy while performing little better than always predicting the majority class.

A further reevaluation followed cross-validation rather than replacing it: once cross-validated performance had established that the modeling approach generalizes, one final model per family -- and, separately, one single multiclass model spanning all 84 families at once -- was retrained on the complete dataset with no further held-out split, for deployment. Reevaluating these final models by scoring them against their own training data was deliberately not treated as a generalization check, since a model's performance on the data it was trained on is not an unbiased estimate of accuracy; instead, each saved model was reloaded and confirmed to reproduce bit-identical predictions to what it produced immediately before saving, which validates that saving and loading introduces no error, while the already-computed cross-validated metrics remain the only legitimate estimate of how these final models are expected to perform on a genuinely new sequence.

Finally, the single multiclass architecture itself constitutes an independent reevaluation of whether AMR gene family can be recovered from these features at all, using a different classification design rather than more data or different features. Cross-validated the same way as the one-vs-rest models (five-fold, grouped, stratified), it was evaluated on top-1 accuracy and both macro- and weighted-averaged F1 across all 84 classes simultaneously, with per-family recall reported specifically so its performance could be compared directly against the corresponding one-vs-rest family's own cross-validated result, rather than only against itself.

# Exploratory analysis of family relationships

Principal component analysis was applied separately from, and was never used as an input to, the classification pipeline described above. It was carried out in a different notebook, on a different unit of analysis -- one averaged feature vector per family (a centroid), not one vector per sequence -- purely to visualize how the 84 reliably-sized gene families relate to each other in feature space, and to check which raw features actually drive that structure. No dimensionality reduction from this analysis was ever fed back into training or evaluating the one-vs-rest or multiclass classifiers; those were trained on the full, un-reduced feature set throughout.

## Centroid construction and component structure

Family centroids were built by standardizing each of the 5,479 individual sequences' feature values first, at the population level, and only then averaging within each family -- deliberately not standardizing the centroids themselves afterward, so that the resulting scale reflects each family's position relative to the whole sequence population rather than relative to the other centroids alone. Principal component analysis was fit fresh on only the 84 families with at least 10 sequences, rather than fit across all 396 families and then subset, so that rare, unreliable families could not distort the component directions. Twenty components were computed across 1,038 features. The first two components explain a modest 10.2% and 7.3% of variance respectively (17.5% combined), confirming directly that this structure is not a two-axis story: cumulative variance across all 20 computed components reaches 65.8%, meaning a meaningful share of family-distinguishing structure sits outside the first two components alone and would be invisible in a conventional PC1-versus-PC2 plot.

This was made concrete rather than left as an abstract concern: for each family, the single component on which it scores most strongly (by absolute value) was identified. PC1 is this "dominant" component for 24 families and PC2 for 20, but the remaining 40 families are spread across thirteen different components from PC3 to PC19 -- for example, the small multidrug resistance (SMR) efflux pump family's strongest signal sits on PC3, with a score larger in magnitude than any family's score on PC1 or PC2, and would not appear at all in an analysis that only ever reported the first two components.

## Cosine similarity within dominant-component groups

For every component, the families sharing that component as their dominant axis were grouped, and pairwise cosine similarity was computed between their full 20-component score vectors within each group. This produced a direct, quantitative answer to a question that is easy to assume rather than check: does sharing a dominant component mean two families are actually similar to each other? Mostly, no. PC1's group -- the largest, at 24 families -- has a mean pairwise cosine similarity of only 0.017 (effectively orthogonal on average, ranging from -0.597 to 0.994), and PC2's group of 20 is similarly low, at 0.024. By contrast, PC5's group of just 3 families is tightly clustered, with a mean cosine similarity of 0.538 (range 0.479 to 0.641). Sharing a dominant axis, in other words, says nothing in general about whether a group of families actually resembles each other; some small groups are genuinely coherent, and the largest groups are closer to a loose collection of families that each happen to lean on the same component for unrelated reasons.

## Loadings versus family-discrimination power

A separate comparison tested whether the features that build each component's variance are the same features that actually separate families from each other -- these are not guaranteed to be the same thing, since principal component analysis is unsupervised and has no knowledge of family labels at all. Each feature's family-discrimination power was measured independently with an ANOVA F-statistic (family label as the class, computed across the same 5,479 sequences and 1,038 features used throughout), then compared against that feature's loading on each of the 20 components. The result was a close-to-complete disconnect: of the twenty components, eighteen have zero overlap between their own top 20 highest-loading features and the twenty features with the highest family-discrimination F-statistic globally, and the remaining two components (PC4 and PC7) overlap by only one and two features respectively. Concretely, PC1's single highest-loading feature has an F-statistic of 290.7, while the feature with the single highest family-discrimination F-statistic in the entire dataset does not even appear among PC1's -- or almost any component's -- top loadings at all. The features that define where the variance is are, for the most part, not the features that define where the families are.
