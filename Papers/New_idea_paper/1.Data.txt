## kraken memory mapping

With memory mapping, Kraken2 did not load the complete 95 GB hash database into RAM before classification. It mapped the file into virtual memory and fetched database pages only when needed.

Kraken classification performs essentially random k-mer lookups. Because the database was on a large disk—likely an HDD—this caused:

repeated random disk reads;
many page faults;
process state D, meaning disk-I/O wait;
approximately 45% I/O wait;
mostly idle CPUs despite requesting 64 threads;
only around 35 GB of the database resident after nearly five hours.

The message:

Loading database information... done.

only meant that the database structure was mapped successfully. It did not mean that all 95 GB had physically entered RAM.

After removing --memory-mapping, Kraken2 instead:

Read the database sequentially from disk.
Loaded it into RAM.
Performed random lookups directly in RAM.
Used the CPU threads effectively.

Sequential disk reading is dramatically faster than millions of random HDD accesses.

Your script starts a separate Kraken2 process for every sample, so each sample technically reloads the database. However, after the first run, Linux usually retains much of the database in filesystem cache. Consequently, database loading for samples 2–4 may be substantially faster.

For your system—125 GiB RAM and a 95 GB database—running without --memory-mapping is the correct choice. Memory mapping would make more sense if the database were on a fast NVMe SSD or could not fit into RAM.
